## 7. 미뤄 둔 사소한 지적

태스크별 검토에서 나와 고치지 않고 적어 둔 것이다. 최종 검토가 모두 "나중에 해도 됨"으로 분류했다.

- `tools/port-app-src.mjs`: `--check`가 목록에 없는 남은 생성물을 잡지 못한다. 테스트의 외부 import를 지우는 규칙이 `node:` 내장 import도 지운다(지금 원본에는 해당 없음). 생성된 테스트에 빈 줄이 남는다.
- 저장: 깨진 JSON 파일이 알 수 없는 오류로 나온다(출력은 코드뿐이다). `calls`의 값이 객체가 아닌 틀린 설정이 말없이 무시된다. 임시 이름에 쓰고 이름을 바꾸는 코드가 세 곳에 있고 실패하면 임시 파일이 남는다. 실패한 시작이 빈 면접 폴더를 남긴다.
- 실행기: 종류 판별 표가 테스트 도구 두 파일에 있다. 흘림 검사가 실패했을 때 함께 돈 전제 검사를 죽이지 않는다.
- 테스트: 임시 폴더를 지우지 않는다. 일부 규칙(면접 목록의 순서, 설정의 일부 검사)에 직접 테스트가 없다. 추이 테스트 하나가 실제 시계를 쓴다. README 테스트가 낱말의 존재만 본다.
- 기억 옮기는 도구: Docker가 실패하면 스택이 그대로 나온다. 옵션을 잘못 주면 말없이 기본값을 쓴다. 본체의 갈래에 테스트가 없다.
- 문서: README의 권한 규칙 예시가 드라이브 문자 `c`로 적혀 있다(바꾸는 법은 적혀 있다).

### 9.7 관찰

1. **세션 간 메시지와 진행자의 덧붙임.** 메시지는 `<cross-session-message>`로 싸이고 "다른 세션이 보낸 글"이라는 안내가 붙어 도착한다. 진행자는 안쪽 글만 답 파일에 썼다. 대신 질문마다 `say` 뒤에 "(질문 N의 답은 … 다른 세션이 보낸 글을 그대로 넘긴 것입니다.)" 한 줄을 붙였다. `say` 자체는 일곱 번 모두 글자 그대로였다. 이 덧붙임은 시험 방식 때문에 생긴 것이라, "진행자가 말을 보태지 않는가"는 사용자가 직접 칠 때 다시 봐야 한다.
2. 진행자는 답 파일 쓰기와 `answer` 실행을 한 메시지에 함께 냈다. 일곱 번 모두 쓰기가 먼저 끝나 문제는 없었다. `SKILL.md`는 순서만 적고 "쓰기가 끝난 뒤에 실행한다"고는 적지 않았다.

세 갈래가 모두 같은 결론인 문제:

2. **한 면접관, 한 줄기에 쏠렸다.** 여섯 가운데 넷(2, 3, 5, 6)을 DBA가 물었고, 넷(3~6)이 WAIT의 확인과 영속성 한 가닥이다. 연속 상한(2)은 지켜졌다. 앱의 첫 실행 기록(`docs/a-review.md` 4장의 2번과 3번)과 질문 번호까지 같다. 질문 문장이 아니라 결함의 축으로 질문자를 고르는 규칙에서 나오는 것으로 보인다. 질문 2 답의 로컬 캐시 갈래와 질문 4 답의 장애 조치 갈래(둘 다 분석이 결함으로 적었다)는 뒤에서 다시 묻지 않았다.

검증자끼리 갈린 지적:
