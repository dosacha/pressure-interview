## 3. 지금 할 일

### 3.1 [결정] 호출·비용 줄이기 1번부터 한다

사용자 원문(2026-11-18): "1부터 시작. 단, 여태까지 작업한 모든 내용을 인수인계하는 프롬프트부터 생성해라."

여기서 "1"은 앞 세션이 제시한 선택지 1번, **프롬프트 캐싱 + 흘림 검사와 전제 검사의 동시 실행**이다. 호출 수는 그대로 두고, 품질을 건드리지 않으면서 비용과 대기를 줄이는 변경이다. 호출 수 자체를 줄이는 방법(정답지 검증을 빼거나 복기 때로 미루기, 답 분석과 질문 생성을 한 호출로 합치기)은 사용자가 고르지 않았다. 하지 않는다.

**(가) 프롬프트 캐싱**

- 지금은 캐싱을 쓰지 않는다. `LlmService.callJson`이 `system: req.system`(문자열)과 user 메시지 하나를 `client.beta.messages.create`로 보낸다(`betas: ['server-side-fallback-2026-07-01']`, `fallbacks: 'default'`).
- 호출마다 똑같이 보내는 시스템 프롬프트의 크기(앞 세션이 코드로 잰 글자 수. 한국어 프롬프트는 글자당 약 1토큰으로 실제 입력 토큰과 맞았다): 질문 5,721 / 답 분석 3,882 / 복기 2,234 / 정답지 검증 1,913 / 흘림 검사 1,095 / 정답지 작성 820 / 전제 검사 794.
- 질문 프롬프트는 교과형 면접관일 때만 시스템 프롬프트 앞쪽(약 1,170자 지점)에 문단 하나(`TEXTBOOK_PERSONA`)가 끼어든다. 그대로 캐싱하면 교과형 차례마다 뒤쪽 4,500자가 캐시에서 빗나간다. 달라지는 부분을 고정 부분 뒤로 보내거나 블록을 나눠야 한다. 프롬프트의 뜻은 바꾸지 않는다.
- 캐싱 규칙은 claude-api 스킬의 `shared/prompt-caching.md`와 `shared/models.md`에서 확인한 것이다: Opus 5.5의 캐시 읽기는 기본 입력가의 0.05배, 쓰기는 5분 TTL 1.25배·1시간 TTL 2배, 캐시할 수 있는 최소 길이 512토큰(문서가 "최신 문서를 확인하라"고 단서를 달았다). 사용량 응답에는 `cache_creation_input_tokens`, `cache_read_input_tokens`가 따로 오고 `input_tokens`에는 캐시된 부분이 빠진다. **구현 전에 claude-api 스킬을 불러 문서를 다시 읽는다.** 기억으로 쓰지 않는다. 구조화 출력, 폴백 베타와 함께 쓸 때의 제약도 거기서 확인한다.
- 그래서 사용량 기록도 고쳐야 한다: `usageRows`(같은 파일), `llm_usage` 테이블(캐시 토큰 칸이 없다. 마이그레이션 필요), `UsageService.summarize`, 복기 화면의 사용량 표. 고치지 않으면 비용 계산이 실제보다 적게 나온다.
- 예상 효과: 어제 한 판 기준 입력 약 6.8만 토큰, 약 $0.27(19%) 절감. 시스템 프롬프트만 캐시하고 5분 TTL로 계산한 **추정값**이다. 답을 5분 넘게 쓰면 캐시가 만료돼 덜 줄어든다. TTL을 어떻게 할지는 구현할 때 [제안]으로 정하고 사용자에게 알린다.
- 실제로 캐시가 맞는지는 유료 실행에서 `cache_read_input_tokens`가 0보다 큰지로만 확인할 수 있다.

**(나) 흘림 검사와 전제 검사를 동시에**

- `src/interview/turn.service.ts`의 `prepareDraft`는 지금 질문 생성 → 흘림 검사(`detectTechs`) → 이름 검사(`checkNaming`) → (이름 검사를 통과했고 가정을 바꾼 질문이면) 전제 검사(`checkPremise`) 순서로 차례로 부른다.
- 가정을 바꾼 질문에서 흘림 검사와 전제 검사를 함께 시작하면 그 질문의 대기가 2~3초 줄 것으로 본다(추정. 흘림 검사 2.0~3.4초, 전제 검사 3.7·7.9초였다).
- 바뀌는 동작: 지금은 이름 위반이면 전제 검사를 부르지 않는다. 동시에 돌리면 이름 위반일 때 전제 검사 한 번이 헛돈다. 두 번의 유료 실행에서 이름 위반은 0건이었다. `turn.service.spec.ts`의 "prepareDraft는 이름 위반이면 전제를 검사하지 않고 다시 만든다" 테스트와 `attempts[].premise`의 뜻("이름 검사에서 걸렸으면 null")을 함께 정리해야 한다. 이름 위반일 때의 피드백은 지금처럼 이름 위반 쪽을 쓴다.

- **서브에이전트는 한 번에 하나, 많아야 둘.** 최상위 모델 다섯을 동시에 돌려 5시간 사용량 한도를 7분에 다 쓴 적이 있다. opus나 sonnet을 쓴다.
- 미추적 파일을 지우거나 reset·clean을 하지 않는다. 다른 프로젝트의 Docker 자원(`apt-os-db-1` 등)을 건드리지 않는다. 이 프로젝트의 이름은 `pressure-interview*`만 쓴다.
- commit은 작업 브랜치에서 한다(승인된 범위). merge, push, 배포는 그때마다 묻는다.
- 사용자는 한국어로 협업하고, 원격(Remote Control)으로 볼 때가 많다. 마지막 메시지는 그것만 읽어도 되게 쓰고, 정해 줄 것이 있으면 선택지를 글로 적는다. 결과와 근거를 먼저 말한다.

## 5. 환경에서 알아 둘 것

- Windows 11, PowerShell 5.1이다. `&&`가 안 되고 `npm`이 실행 정책에 걸리면 `npm.cmd`를 쓴다. Git Bash도 쓸 수 있다.
- 포트: 앱 3110, 개발 DB 5436, 가짜 응답 앱 3199. 이 PC에서 3100과 5435는 다른 것이 쓰고 있다.
- `.gitattributes`가 `eol=lf`다. 파일을 CRLF로 저장하면 포맷 검사에 걸린다.
- Node 24.21 이상. 단위 테스트는 Jest, 프런트 테스트는 `node:test`, e2e는 `scripts/run-e2e.ts`가 임시 컨테이너(`pressure-interview-e2e-<pid>-<시각>`)를 띄웠다가 지운다.
- `src/interview/types.ts`에 면접관 고르기 결과인 `interface Pick`이 있어 TS의 유틸리티 `Pick`을 가린다.
- 가짜 응답 앱은 Ctrl+C나 `GET /__fake/stop`으로 끈다. Windows에서 프로세스를 강제로 죽이면 임시 DB 컨테이너가 남는다.
- 화면 확인은 내장 브라우저로 했다. 주소의 hash만 바꾸면 문서가 새로 불러와지지 않으므로 `?r=<아무 값>`을 붙여 새로 불러온다.
- 사용자의 `.env`는 질문 생성·검증 effort를 medium으로 둔다(사용자 [결정]). 복기는 설정이 없으면 기본값 high다.

## 6. 구조 한눈에

- `src/interview/` 엔진. `calls/`에 호출별 프롬프트와 스키마(question, answer-key, premise, verify, leak, analyze, clarify, job-role, review), `turn.service.ts`에 `prepareDraft`·`completeQuestion`·`handleAnswer`·`replyToClarification`·`reviewTurn`, `rules.ts`에 다음 질문자를 고르는 규칙, `llm/`에 모델 호출과 사용량 기록.
- `src/session/` 면접 한 판. `interview.service.ts`가 "DB를 보고 빠진 단계를 한다"는 방식으로 진행하고, 세션별 잠금과 뒤 작업(정답지 작성·검증)을 다룬다. `interview.view.ts`는 면접 중에 내보내도 되는 값만 고른다.
- `src/review/` 복기 서비스·API·추이. `src/memory/` 가정별 기억. `src/usage/` 사용량 집계.
- `frontend/web/` 화면(시작, 면접, 복기, 추이). 서버 응답은 `lib/decode.ts`와 `lib/review-decode.ts`로 경계에서 검사한다.
- `scripts/` e2e 실행기, 가짜 응답 앱, R1 실행기. `test/` e2e와 가짜 Anthropic 클라이언트(`test/support/fake-anthropic.ts`, 요청 스키마의 `required` 키로 호출 종류를 가린다).

면접 한 판의 호출 흐름: 시작할 때 직무 고르기 1회. 질문마다 질문 문장 생성 → 흘림 검사 → (가정을 바꾼 질문이면) 전제 검사 → 화면. 그 뒤 뒤에서 정답지 작성 → 정답지 검증. 답이 오면 정답지가 준비될 때까지 기다린 뒤 답 분석 → 규칙으로 다음 질문자와 반응을 정함 → 다음 질문. 되묻기는 분석 → 응답 → 흘림 검사.
