## 1. 의도

앱(NestJS 서버 + PostgreSQL + 화면 + Anthropic API 키)으로 만든 압박 면접 연습 도구를, 서버 없이 Claude Code 세션 안에서 도는 스킬로 다시 만든다. **[결정]**

까닭(사용자의 말에서 정리): 띄울 것이 없고, API 과금 대신 구독 한도 안에서 쓴다. 면접의 규칙은 앱과 같다. 달라지는 것은 그 규칙을 돌리는 자리뿐이다.

면접이 단련하려는 것, 성공 기준(S1·S2), 실패 조건(F1~F4)은 앱 설계 1~2장 그대로다. 이 문서는 그것을 다시 정하지 않는다.

## 2. 목표, 비목표, 실패 조건

**목표**

- 앱의 면접 한 판(시작 → 질문 → 답 → 다음 질문 → 끝 → 복기 → 기억)을 같은 규칙과 같은 프롬프트로 스킬에서 돌린다.
- 질문 의도, 정답지, 결함 판정, 반응 의도, 면접관의 성향이 면접 중에 대화 화면에 나오지 않는다.
- 흘림 검사, 전제 검사, 정답지, 복기가 서로의 컨텍스트를 모르는 별도 호출이다. **[결정]** 정답지 검증과 답 분석도 앱과 같게 별도 호출로 둔다.
- 복기와 추이를 문서로 만든다. **[결정]**
- 한 판이 호출을 몇 번 하고 토큰을 얼마나 썼는지 기록에 남는다.

**비목표**

- 서버, DB, 웹 화면. **[결정]**
- 답 시작 시간 재기. **[결정]** 추이에서도 뺀다.
- 앱을 고치거나 없애기. 앱은 그대로 둔다. **[결정]**
- 프롬프트의 뜻을 바꾸기. 앱의 프롬프트를 글자 그대로 옮긴다(8장).
- 지금 마켓플레이스에 올려 배포하기. 구조만 플러그인에 맞춘다. **[결정]**
- Claude Code가 아닌 하니스(Codex, Cursor 등), 구독 로그인이 아닌 인증(Bedrock, Vertex, API 키) 지원. **[제안]**
- 앱 설계의 비목표(서류 기반 2단계, 음성, 코딩 테스트, 다중 사용자).

**실패 조건** (돌아가더라도 이러면 실패다)

- **K1** 숨길 내용이 면접 중에 대화 화면에 나온다.
- **K2** 진행자(주 세션)가 면접관 대신 말을 지어내거나, 답에 평을 하거나, 가르친다.
- **K3** 다음 질문자와 반응 의도를 모델이 고른다. 앱에서 코드였던 규칙은 스킬에서도 코드다.
- **K4** 프롬프트가 옮기는 중에 달라진다.
- **K5** 사용자가 모르는 사이에 API 과금으로 호출이 나간다.

## 3. 제약

- 사용자의 PC: Windows 11, Node 24, Claude Code 2.1.326(명령줄 `claude.exe`가 설치돼 있고 구독으로 로그인돼 있다. 2026-11-18 확인). 세션은 데스크톱 앱의 Code 탭과 터미널 둘 다 쓴다.
- 호출은 구독 한도를 쓴다. 한 판이 한도를 얼마나 쓰는지는 재 본 적이 없다. README에 호출 횟수를 밝히고 사용자의 선택으로 둔다. **[결정]**
- 숨김은 약속이다. 숨길 내용은 사용자가 정한 폴더의 파일에 있고, 사용자가 열면 보인다. **[결정]**
- 스킬 본문은 대화가 압축되면 앞 5,000토큰만 다시 붙는다(공식 문서). 진행 상태를 대화에 두면 안 된다.
- 스킬의 `allowed-tools` 사전 허용은 스킬을 부른 턴에만 유효하다(공식 문서). 답을 넘기는 턴은 스킬을 부른 턴이 아니다. 그 턴의 명령 실행과 파일 쓰기는 사용자의 권한 설정을 따른다(9장).
- 진행자가 쓰는 명령 실행 도구에는 시간 제한이 있다(기본 2분, 최대 10분).

## 4. 접근 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 서브에이전트 | 주 세션이 호출마다 서브에이전트를 띄운다. 숨길 내용은 파일로만 오가고 주 세션은 경로만 넘긴다 | 추가 설치가 없다. 진행이 화면에 보인다 | 서브에이전트 하나가 약 8만 토큰을 썼다(이 PC, 1회 측정). 백그라운드 서브에이전트의 권한 창이 답을 쓰는 중에 뜰 수 있다. 단계마다 주 세션의 턴이 든다 |
| **B. 스크립트가 `claude -p`를 부른다** **[결정: 선택]** | 스킬의 Node 스크립트가 호출마다 `claude -p`(한 번 묻고 끝나는 실행)를 따로 띄운다. 주 세션은 스크립트 하나를 돌리고 화면에 낼 것만 받는다 | 호출마다 새 프로세스라 격리가 A와 같다. 호출당 붙는 토큰이 약 1,300이다(1회 측정). 호출이 도구를 쓰지 않는다. 출력 모양이 강제된다(`--json-schema`). 호출별 토큰 수가 남는다. 엔진의 출력에 숨길 내용이 실리지 않는다. 앱의 진행 코드를 거의 그대로 옮길 수 있다 | `claude` 명령줄이 설치·로그인돼 있어야 한다. CLI 옵션이 바뀌면 깨질 수 있다. 진행은 "스크립트 실행 중"으로만 보인다 |
| C. 주 세션이 직접 다 한다 | 서브 호출 없이 한 대화에서 질문, 정답지, 분석을 모두 한다 | 만들 것이 가장 적다 | 숨김과 독립 검사가 사라진다. 사용자가 이미 버린 방식이다 |

B를 고른 까닭: 사용자가 정한 것(별도 호출, 파일로 숨김, 구독 한도)을 모두 지키면서 한도를 가장 적게 쓴다. K3은 구조로 막힌다(규칙이 코드다). K1은 절반이 구조로 막힌다. 엔진의 출력에는 숨길 내용이 실리지 않는다. 그러나 주 세션은 파일을 읽을 수 있으므로, 숨긴 파일을 읽지 않는 것은 A와 마찬가지로 지시에 기댄다(5.2).

사용자가 처음 정한 문구는 "서브에이전트"였다(인수인계 4장). 2026-11-18에 두 방식의 측정값을 보고 B로 바꿨다. **[결정]**

## 5. 구조

### 5.1 세 부분

1. **진행자 = 주 세션.** `SKILL.md`를 따른다. 하는 일은 셋뿐이다: 엔진 명령을 돌린다, 엔진이 준 문장을 그대로 보여 준다, 사용자의 답을 그대로 엔진에 넘긴다.
2. **엔진 = Node 스크립트.** 앱에서 코드였던 것 전부다. 한 판의 순서, 다음 질문자를 고르는 규칙, 이름 검사, 기억, 복기 문서 만들기, 추이 계산. 모델이 필요한 곳에서만 `claude -p`를 부른다. **[결정: Node, 의존성 없음]**
3. **호출 = `claude -p` 한 번.** 앱의 아홉 호출을 그대로 둔다(5.3). 호출마다 시스템 프롬프트, user 메시지, 출력 스키마, 모델, effort를 엔진이 정한다.

### 5.2 진행자와 엔진 사이의 약속 [제안]

엔진은 명령 하나를 끝낼 때 표준 출력에 JSON 한 덩어리만 낸다. 거기에는 화면에 내도 되는 것만 들어간다.

```json
{
  "ok": true,
  "kind": "question",
  "interview": "2026-11-19-1432-redis",
  "say": "**질문 3/6 · DBA 면접관**\n\n방금 말씀하신 구성에서 …",
  "answerFile": "C:/…/2026-11-19-1432-redis/answers/03-1.txt",
  "next": "사용자의 다음 메시지를 answerFile에 글자 그대로 쓰고 answer를 실행한다."
}
```

- `say`: 진행자가 덧붙이거나 고치지 않고 그대로 보여 줄 문장. 질문, 되묻기 응답, 마무리 말, 안내.
- `next`: 진행자가 다음에 할 일 한 줄. 대화가 압축돼 `SKILL.md`의 뒤쪽이 사라져도 면접이 이어지게 하려고 매번 싣는다.
- 화면에 내는 면접관 표시는 직무 이름까지다("DBA 면접관", "교과형 면접관"). 성향은 숨긴다. 앱의 화면과 같다.

**실패할 때의 출력.** `{"ok": false, "code": "...", "say": "...", "next": "..."}`만 낸다. 코드는 정해진 낱말이다: `usage_limit`(구독 한도), `refused`(모델이 거절), `schema_failed`(출력이 스키마와 안 맞음), `timeout`, `cli_missing`(`claude`를 못 찾음), `not_logged_in`, `interview_open`, `not_finished`, `not_reviewed`, `no_answer`, `other`.

- 엔진은 표준 오류에 아무것도 쓰지 않는다. 진입점이 잡히지 않은 예외와 거부된 Promise까지 모두 잡아, 원래 오류는 `hidden/errors.log`에만 쓰고 화면에는 코드만 낸다. `claude -p`의 표준 출력과 표준 오류는 엔진이 받아서 처리하고 그대로 흘려보내지 않는다. 모델 응답을 파싱하다 난 오류의 문장에는 응답 글자(정답지일 수 있다)가 섞이기 때문이다. 앱이 원래 오류를 서버 로그에만 남긴 것과 같은 까닭이다.
- 실패의 `next`에는 "`hidden/`과 `errors.log`를 읽지 말고 사용자에게 알린다"가 들어간다. 진행자가 원인을 찾겠다고 숨긴 파일을 여는 것을 막기 위해서다.

**진행자가 지킬 것**(`SKILL.md`의 맨 앞에 둔다): 면접 폴더의 `hidden/`을 읽지 않는다. `say`에 말을 보태지 않는다. 답에 평을 하지 않는다. 이것은 지시다. 구조로 막히지 않는다.

**답을 넘기는 방법.** 진행자가 사용자의 메시지를 `answerFile`에 파일 쓰기 도구로 글자 그대로 쓴 뒤 `answer`를 실행한다. 명령 인자로 넘기면 따옴표와 줄바꿈이 깨질 수 있어서다.

- `answerFile`의 이름은 매번 새것이다(질문 번호와 그 질문에서 몇 번째 입력인지). 파일 쓰기 도구는 읽지 않은 기존 파일을 덮어쓰지 못하고, 앞 답이 남아 있으면 다시 들어갈 수 있기 때문이다.
- 엔진은 그 파일을 읽어(BOM을 떼고 줄바꿈을 LF로 맞춘다) 턴에 저장한 뒤 지운다. 파일이 없거나 비어 있으면 `no_answer`로 거절한다.
- 답이 이미 저장된 턴에서 `answer`를 다시 돌리면 답을 새로 읽지 않고 빠진 단계부터 이어 간다. 도구의 시간 제한에 걸려 명령이 죽어도 답이 두 번 들어가지 않는다.

### 5.3 호출 아홉 가지와 누가 무엇을 보는가

앱과 같다. 입력은 앱의 각 호출이 user 메시지에 싣던 것 그대로다.

| 호출 | 보는 것 | 보지 않는 것 | 모델 | effort |
|---|---|---|---|---|
| 직무 고르기 | 주제 | | sonnet | medium |
| 질문 문장 | 주제, 면접관의 직무와 성향, 지금까지의 대화, 지원자가 말한 기술, 모른다고 한 기술, 기억의 가정 목록, 이번 질문의 지시(반응 의도, 결함 유형·축·한 줄 메모, 가정 축, 덧붙임 여부), 앞 시도의 지적 | 정답지 전부 | opus | medium |
| 흘림 검사 | 질문 문장과 지원자가 말한 기술. 되묻기 응답을 검사할 때는 응답 문장과, 말한 기술에 그 질문에서 검출된 기술을 더한 목록 | 그 밖의 모든 것 | sonnet | low |
| 전제 검사 | 주제, 질문 문장, 바뀐 가정(축과 문장) | 질문 의도, 대화, 정답지 | opus | medium |
| 정답지 작성 | 주제, 면접관, 반응 의도, 결함, 덧붙임 여부, 그 질문 전까지의 대화, 질문 초안(문장, 의도, 가정) | 질문을 쓸 때의 지시(말한 기술, 기억, 지적) | opus | medium |
| 정답지 검증 | 주제, 질문 초안, 정답지 | 대화 | opus | medium |
| 답 분석 | 주제, 지원자가 이전까지 말한 기술, 질문 초안, 정답지, 지원자의 입력 | 앞의 대화, 면접관의 성향 | opus | medium |
| 되묻기 응답 | 주제, 면접관의 직무, 질문 문장, 바뀐 가정의 문장, 앞선 되묻기, 이번 되묻기, 말한 기술, 모른다고 한 기술, 앞 시도의 지적 | 정답지, 질문 의도, 성향, 검출된 기술 | opus | medium |
| 복기 | 주제, 면접관, 질문이 나온 까닭, 질문과 정답지, 되묻기, 답, 면접 중 분석, 그 답에서 나온 질문들, 같은 축의 알려진 가정 | | opus | high |

- 모델 배정은 **[결정]**(흘림 검사와 직무 고르기는 sonnet, 나머지는 opus). effort는 앱의 값이다. **[결정: 앱과 같게]**
- 모델과 effort는 설정 파일에서 호출 종류별로 바꿀 수 있다. **[결정]** 기본값은 별칭(`opus`, `sonnet`)이고, 실제로 응답한 모델 이름을 호출 기록에 남긴다. **[제안]** 프롬프트는 `claude-opus-5-5`로 다듬은 것이다. sonnet으로 도는 두 호출의 품질은 확인한 적이 없다(11장).

### 5.4 `claude -p`를 부르는 방법 [제안]

호출 하나는 다음과 같다. 2026-11-18에 이 옵션들로 실제 호출이 됐다(12장).

```
claude -p --model <모델> --effort <effort> --system-prompt-file <파일>
       --json-schema <스키마> --output-format json --tools ""
       --safe-mode --no-session-persistence --strict-mcp-config
```

- user 메시지는 표준 입력으로 넣는다. 결과는 JSON의 `structured_output`에서 읽는다. 셸을 거치지 않고 띄운다.
- `--tools ""`: 도구가 없다. 호출은 파일을 읽을 수도, 권한을 물을 수도 없다.
- `--safe-mode`: 사용자의 CLAUDE.md, 스킬, 플러그인, 훅, MCP 서버를 싣지 않는다. 조직이 관리하는 정책 설정과 관리 플러그인의 훅은 남는다(CLI 도움말).
- `--no-session-persistence`: 호출 기록을 Claude Code의 세션 목록에 남기지 않는다. 숨길 내용이 남는 곳은 면접 폴더뿐이다.
- **자식 프로세스의 환경.** `ANTHROPIC`으로 시작하는 변수와 `CLAUDE`로 시작하는 변수를 지운다. 남기는 것은 `CLAUDE_CONFIG_DIR`(로그인 정보의 위치)과 설정의 `keepEnv`에 적은 이름뿐이다. 까닭은 둘이다. 셸에 `ANTHROPIC_API_KEY`가 있어도 API 과금으로 나가지 않게 한다(K5). 세션이 물려준 변수를 통해 호출이 지금 세션에 엮이지 않게 한다. 측정한 호출은 한 번을 빼고 모두 이렇게 지운 환경에서 돌았다(12장).
- K5는 환경 변수만으로 다 막히지 않는다. 설정 파일을 통한 API 키 인증은 남을 수 있다. 그래서 점검 명령이 `claude auth status`로 구독 로그인인지 확인하고, 아니면 면접을 시작하지 않는다.
- **실패.** 종료 코드가 0이 아니거나, 결과가 오류이거나, `structured_output`이 없거나, 시간 상한을 넘으면 그 단계의 실패다. 엔진은 스스로 다시 부르지 않는다. 저장된 상태가 그대로 남으므로 빠진 단계부터 다시 할 수 있다(6.5). 실패의 종류(5.2의 코드)는 구분할 수 있는 만큼 구분하고 못 하면 `other`다. 한도, 거절, 스키마 불일치일 때 결과가 어떤 모양인지는 아직 본 적이 없다(11장).
- `claude`의 위치와 실행 방법은 설정의 `claudeCommand`(문자열 배열, 기본 `["claude"]`)로 바꿀 수 있다. 테스트는 이것을 가짜 실행기로 바꿔 한도를 쓰지 않는다(10장). npm으로 설치해 `claude.cmd`인 경우는 셸 없이 띄울 수 없으므로 이 설정으로 푼다(README에 적는다).

### 5.5 파일 [제안]

설정 파일은 홈에 하나 둔다: `~/.pressure-interview/config.json`. 면접 폴더의 위치, 호출별 모델과 effort, 질문 수(기본 6), 같은 면접관 연속 상한(2), 다시 만들기(1회), 다시 내기 간격(24시간), 복기의 동시 호출 수(3), `claudeCommand`, `keepEnv`가 들어간다. 기본값은 앱과 같다.

면접 폴더는 사용자가 처음 부를 때 정한다. **[결정]** 그 폴더 하나에 모두 둔다.

```
<면접 폴더>/
  memory.json                 가정 기억
  stats.md                    추이 문서
  interviews/
    2026-11-19-1432-redis/    면접 하나
      answers/03-1.txt        진행자가 답을 써 넣는 자리 (엔진이 읽고 지운다)
      review.md               복기 문서 (복기가 모두 끝난 뒤에 생긴다)
      hidden/                 면접이 끝나기 전에는 열지 않는 곳
        session.json          주제, 패널(직무와 성향), 질문 수, 상태, 말한 기술, 모른다고 한 기술, 기다리는 덧붙임, 이 면접에 실은 기억
        calls.jsonl           호출 기록 (종류, 모델, effort, 토큰, 걸린 시간)
        errors.log            실패의 원래 오류
        turns/
          03/
            question.json     질문 초안(문장, 의도, 가정), 나온 까닭, 시도 기록, 흘림·전제 표시
            key.json          정답지, 검증 결과, 고쳐졌는지
            key.lock          정답지를 쓰는 중이라는 표시 (6.4)
            answer.json       답, 되묻기 기록, 분석, 다음 질문자를 고른 결과
            review.json       복기 결과, 사용자가 고친 가정 결과, 예상 표시
```

- 턴마다 파일을 나누는 까닭: 정답지는 뒤에서 도는 프로세스가 쓰고 답은 앞의 명령이 쓴다. 파일마다 쓰는 쪽을 하나로 두면 서로 덮어쓰지 않는다. `key.json`은 `key.lock`을 쥔 쪽만 쓴다(6.4).
- `calls.jsonl`과 `errors.log`는 여러 프로세스가 한 줄씩 붙여 쓰는 파일이다.
- 그 밖의 파일은 임시 이름으로 쓴 뒤 이름을 바꿔 넣는다. 쓰다 죽어도 반쯤 쓴 파일이 남지 않는다.
- 면접 id는 `날짜-시각-주제`다. 주제 부분은 폴더 이름에 쓸 수 있는 문자만 남기고 길이를 자른다. 같은 이름이 있으면 번호를 붙인다. 원래 주제는 `session.json`에 둔다. 턴은 순번으로 가리킨다(앱의 UUID 대신).

## 6. 면접 한 판

앱의 `InterviewService`와 `TurnService`를 그대로 옮긴다. 아래는 그 흐름을 스킬의 명령으로 적은 것이다.

### 6.1 명령 [제안]

사용자가 치는 것은 슬래시 명령 하나다. **[결정: 이름은 `pressure-interview`]**

| 사용자가 치는 것 | 하는 일 |
|---|---|
| `/pressure-interview <주제>` | 새 면접을 시작한다 |
| `/pressure-interview` | 상태를 보여 준다: 진행 중인 면접, 다시 연습할 가정이 남은 주제, 최근 면접과 그 id |
| `/pressure-interview 이어서` | 진행 중인 면접을 이어 한다. 열린 질문이 있으면 다시 보여 주고, 앞에서 실패해 멈춘 곳이 있으면 거기서부터 한다 |
| `/pressure-interview 끝` | 지금 면접을 일찍 끝낸다 |
| `/pressure-interview 복기 [면접 id]` | 끝난 면접의 복기 문서를 만든다 |
| `/pressure-interview 고침 <질문 번호> <잘답함/흔들림/틀림> [면접 id]` | 가정 결과를 고치고 기억을 다시 맞춘다 |
| `/pressure-interview 표시 <질문 번호> <예상/예상밖> [면접 id]` | 예상 표시를 남긴다 |
| `/pressure-interview 추이` | 추이 문서를 다시 만들어 보여 준다 |

- **진행 중인 면접은 하나만 둔다. 달라짐.** 앱은 여럿을 둘 수 있었다. 스킬은 "지금 열린 질문"이 하나여야 사용자의 메시지를 어디에 넣을지 정해진다. 진행 중인 면접이 있는데 새 주제로 시작하면 `interview_open`으로 거절하고 `이어서`나 `끝`을 안내한다. 앞 면접을 말없이 버리지 않는다.
- **질문이 열려 있는 동안 사용자의 메시지는 모두 답이다.** 진행자는 그 글을 판단하지 않고 그대로 엔진에 넘긴다. 되묻기인지 답인지는 앱처럼 답 분석 호출이 가른다. 면접을 멈추거나 다른 일을 시키려면 위의 슬래시 명령을 쓴다. 진행자가 "이건 답이 아닌 것 같다"고 판단하게 두면 답이 엔진에 닿지 않는 경우가 생긴다.
- 엔진이 도는 중에 사용자가 보낸 메시지는 답으로 넘기지 않는다. 다음 질문을 보여 준 뒤, 그 메시지를 어떻게 할지 사용자에게 묻는다. 앞 질문에 덧붙인 말이 새 질문의 답으로 들어가는 것을 막는다.
- `복기`, `고침`, `표시`는 면접 id가 없으면 가장 최근에 끝난 면접을 가리킨다. 끝나지 않은 면접에는 `not_finished`로 거절한다. 진행 중에 복기가 돌면 열린 질문의 의도와 정답지가 드러나기 때문이다. `고침`과 `표시`는 복기가 끝난 면접에만 한다(`not_reviewed`).
- 첫 인자가 위 표의 낱말이면 명령으로, 아니면 인자 전체를 주제로 본다.
- 처음 부를 때 설정 파일이 없으면 면접 폴더를 먼저 묻는다. **[결정]**
- 스킬은 사용자가 불러야만 돈다(`disable-model-invocation: true`). 대화 중에 모델이 알아서 면접을 시작해 한도를 쓰는 일을 막는다.
- 진행자는 엔진 명령을 `node "<스킬 폴더>/scripts/cli.mjs" <명령> …` 한 가지 꼴로, Bash 도구로 돌린다(Bash 도구가 없으면 PowerShell 도구로 같은 줄을 돌린다). 도구의 시간 제한은 최대(10분)로 준다. `answer` 한 번에 호출이 여럿 이어지고 복기는 몇 분이 걸릴 수 있어서 기본 2분을 넘을 수 있다.

### 6.2 시작

1. 점검: `claude`가 있는가, 구독으로 로그인돼 있는가.
2. 기억에서 이번 면접에 실을 가정을 고른다(잘 답한 것 30개, 다시 낼 것 5개, 예상했던 것 10개 상한, 다시 내기는 마지막 만남에서 24시간 뒤. 앱과 같다).
3. 직무 고르기 호출 → 패널 셋(직무형 하나, 교과형, 시나리오형)과 무작위 성향 → 여는 면접관을 무작위로 고른다. "지원자가 말한 기술"은 주제 하나로 시작한다(앱과 같다. 주제 기술을 모른다고 해도 넘어가지 않는 규칙이 여기에 기댄다).
4. 첫 질문을 준비한다(6.3) → 저장 → 정답지 작업을 뒤에서 시작한다(6.4) → 질문을 출력한다.

### 6.3 질문 준비

앱의 `prepareDraft`다.

1. 질문 문장 호출.
2. 흘림 검사와 전제 검사를 함께 시작한다. 전제 검사는 가정을 바꾼 질문일 때만 한다.
3. 이름 검사(코드). 가정 없는 질문에서 전제로 분류된 기술은 해답으로 본다.
4. 이름 검사에 걸리면 그 지적을, 이름 검사는 통과했는데 전제 검사가 틀렸다고 하면 그 지적(문제 문장이 비어 있으면 앱의 고정 문장)을 붙여 한 번 다시 만든다. 이름 위반이 먼저다. 이름 위반 시도에서 함께 돈 전제 검사의 결과는 버린다.
5. 마지막 시도를 쓴다. 그때도 걸려 있으면 흘림 표시나 전제 표시를 남기고 그대로 낸다(앱과 같다).

### 6.4 정답지 (뒤에서)

질문을 출력하는 명령이, 끝나기 전에 정답지 작성 → 정답지 검증을 하는 프로세스를 떼어 내 띄운다. 사용자가 답을 쓰는 동안 돈다. 끝나면 `key.json`을 남긴다.

**달라짐**: 앱은 서버 안의 비동기 작업이었고 스킬은 따로 뜬 프로세스다. 앱이 메모리 안의 표로 지키던 "한 턴에 정답지 작업은 하나"를 파일로 지킨다. **[제안]**

- 정답지를 쓰려는 쪽은 먼저 `key.lock`을 "없을 때만 만들기"로 만든다(자기 pid와 시각을 적는다). 만든 쪽만 `key.json`을 쓰고, 쓴 뒤 잠금을 지운다. 못 만든 쪽은 쓰지 않는다.
- 뒤 작업은 `key.json`이 없고 살아 있는 잠금도 없을 때만 띄운다. 시작, `answer`, `이어서`가 같은 턴의 뒤 작업을 겹쳐 띄우지 않는다.
- 떼어 낸 프로세스는 입출력을 모두 끊고 띄운다(부모의 출력에 물려 있으면 도구 호출이 끝나지 않거나 정답지 내용이 그 출력에 섞일 수 있다). 그 프로세스의 실패는 스스로 `errors.log`에 쓴다.
- 호출마다 시간 상한이 있으므로 뒤 작업은 언젠가 끝난다. 잠금을 쥔 프로세스가 죽었으면(pid가 없거나 잠금이 상한보다 오래됐으면) 잠금을 치우고 다시 잡을 수 있다.

도구 호출이 끝난 뒤에도 떼어 낸 프로세스가 살아 결과를 남기는 것은 이 PC에서 확인했다(12장).

### 6.5 답

1. 진행자가 답을 `answerFile`에 쓰고 `answer`를 실행한다. 엔진이 답을 턴에 저장한다(5.2).
2. 정답지가 아직 없으면: 뒤 작업이 살아 있으면 끝날 때까지 기다린다. 뒤 작업이 없거나 죽었으면 잠금을 잡고 그 자리에서 만든다. 살아 있는 뒤 작업과 함께 만들지 않는다(앱과 같다).
3. 답 분석 호출 → 코드가 거른다. 이미 말한 기술(주제 포함)의 모름은 넘어가지 않는다. 스스로 꺼내며 모른다고 한 기술은 "말한 기술"에 넣지 않고 "모른다고 한 기술"에 쌓는다. **[결정]** 질문이 꺼낸 기술을 모른다고 하면 같은 면접관이 B11로 넘어간다.
4. 되묻기면: 되묻기 응답 호출 → 흘림 검사 → 걸리면 한 번 다시 → 응답을 출력하고 같은 질문을 다시 연다.
5. 답이면: 질문 수에 닿았으면 끝낸다(마무리 문장은 앱과 같다). 아니면 코드가 다음 질문자와 반응 의도를 고르고(결함 우선순위, 축의 담당, 연속 상한, 덧붙이는 질문, 절반을 넘도록 가정 변경이 없으면 정체성 비교 축 지정) → 6.3 → 6.4 → 질문을 출력한다.

**실패했을 때.** 그때까지 저장된 것은 남는다. 진행자는 실패를 알리고 다시 할지 묻는다. 사용자가 하겠다고 하면 `이어서`와 같은 명령으로 빠진 단계부터 다시 한다. 앱의 "다시 시도" 단추와 같다. 호출을 더 쓰는 일이라 진행자가 알아서 되풀이하지 않는다. `usage_limit`이면 한도가 풀린 뒤에 `이어서`를 치라고 알린다.

### 6.6 끝

질문 수에 닿거나 사용자가 `끝`을 치면 끝난다. 답이나 분석이 없는 마지막 턴은 복기에서 빠진다(앱과 같다). 진행자는 마무리 문장을 보여 주고, 복기를 만들지 묻는다. 복기는 호출이 답한 질문 수만큼 더 나가므로 사용자가 정한다. 앱에서도 "복기 만들기"는 사용자가 누르는 단추였다.

## 7. 복기, 기억, 추이

### 7.1 복기

앱의 `ReviewService`를 옮긴다.

- 복기 대상은 답이 있고 분석이 되묻기가 아닌 턴이다. 대상마다 복기 호출 한 번, 한 번에 셋씩 한다. 모델이 없는 결함·질문·가정을 가리키면 버리는 거름도 그대로다.
- 턴 하나의 실패는 나머지를 멈추지 않는다. `복기`를 다시 치면 복기가 없는 턴만 한다. 이미 복기한 턴을 다시 복기하지는 않는다. 앱에도 그 기능이 없고, 기억의 기록이 갈라질 수 있다.
- 대상 턴이 모두 복기되면 기억을 맞추고(7.2), 복기를 마친 시각을 적고, `review.md`와 `stats.md`를 쓴다. 일부가 실패했으면 문서를 쓰지 않고 몇 개가 남았는지 알린다. **[제안]**
- 기억을 맞추다 실패하면 복기를 마친 시각을 적지 않는다. `복기`를 다시 치면 기억부터 맞춘다(앱과 같다).
- 복기 명령은 앞에서 끝까지 돈다. **달라짐**: 앱은 뒤에서 돌리고 화면이 진행을 물었다.

`review.md`에 담는 것:

- 질문마다: 질문과 면접관(직무, 성향), 되묻기, 내 답, 질문 의도(묶음과 이름), 이 질문이 나온 까닭(반응 의도, 결함과 메모), 답이 의도를 향했는가, 면접 중 판정의 재검사(맞는 판정 / 오판), 이 답에서 나온 질문의 분류(맞는 지적 / 오판 / 의도된 확신 시험 / 더 깊이 물음 **[결정]**), 바뀐 가정과 그 결과(잘 답함 / 흔들림 / 틀림), 정답지(사라지는 차이, 남는 차이, 대안 기술과 특징, 기대하는 답의 핵심, 검증이 고쳤는지), 복기가 찾은 정답지의 문제, 흘림 표시와 전제 표시, 예상 표시.
- 면접 단위: 가정별 결과 표, 복기에서 빠진 답의 수, 호출 기록의 합계(종류별 횟수와 토큰. 앱의 사용량 표와 같다).
- 앱에 없던 것 둘을 더한다 **[제안]**: 호출 종류별 걸린 시간, 그리고 `answer` 명령이 시작해 다음 질문을 낼 때까지 걸린 시간(엔진이 잰 값이다. 진행자가 답을 받아 명령을 돌리기까지의 시간은 들어가지 않는다).
- **달라짐**: 답 시작 시간이 없다. **[결정]**

사용자는 복기를 읽고 가정 결과를 고치거나(`고침`) 예상 표시를 남긴다(`표시`). 문서를 손으로 고치는 방식이 아니라 명령으로 하는 까닭: 문서는 만들어 낸 결과물이고, 기억을 다시 맞추는 일이 함께 일어나야 한다. **[제안]** 조건은 앱과 같다.

- 복기 대상이 아닌 턴은 고칠 수 없다. 가정 결과 고치기는 가정을 바꾼 질문의 턴에만 한다.
- 복기가 가정 결과를 "해당 없음"으로 준 턴이라도, 사용자가 고친 결과는 기억에 넣는다(앱의 [제안]을 이어받는다. `docs/b-review.md` 6장의 F2. 사용자는 아직 답하지 않았다).
- 예상 표시는 복기 대상 턴 어디에나 붙는다. 가정이 없는 질문에도 붙는다.
- 고친 뒤 기억을 다시 맞추고 `review.md`와 `stats.md`를 다시 쓴다.

### 7.2 기억

앱의 규칙 그대로다. 반복의 단위는 바뀐 가정(축 + 기술과 무관한 한 문장)이다. 같은 가정인지는 복기 호출이 가른다. 같은 면접 안의 같은 가정은 묶고 마지막 답의 결과를 쓴다. 틀렸다가 반례를 받고 바로잡은 가정은 잘 답함으로 은퇴한다. **[결정]** 저장은 `memory.json` 하나다.

앱의 개발 DB에 있는 가정 기록을 스킬의 `memory.json`으로 옮긴다. 개발 DB는 읽기만 한다. **[결정]** 한 번 쓰는 도구로 만들고 스킬에는 싣지 않는다. **[제안]**

### 7.3 추이

`stats.md`에 적는다: 흔들림이나 틀림에서 잘 답함으로 바뀐 가정 수, 최근 끝난 면접 열 개의 날짜·주제·"예상 밖" 비율, 다시 연습할 가정이 남은 주제. 답 시작 시간의 중앙값은 뺀다. **[결정]**

## 8. 앱에서 옮기는 것

**기준은 `aeae0dd`의 `src`다**(브랜치 `feat/unknown-tech-volunteered`). "스스로 꺼낸 모름"이 그 커밋에 있기 때문이다. 이 브랜치의 `src`와는 다섯 파일이 다르다: 구현 셋(`analyze.call.ts`, `turn.service.ts`, `types.ts`)과 테스트 둘(`calls.spec.ts`, `turn.service.spec.ts`). 그 브랜치를 이 브랜치에 병합하지는 않는다. 앱 쪽 병합은 사용자가 따로 정한다.

| 앱의 파일 | 스킬에서 |
|---|---|
| `src/interview/catalog.ts` | 그대로 (축, 직무, 성향, 의도 A1~A15·B1~B11, 결함 유형과 우선순위, 반응표) |
| `src/interview/rules.ts`, `naming.ts` | 그대로 (다음 질문자 고르기, 이름 검사) |
| `src/session/session-rules.ts` | 그대로 (패널 구성, 여는 면접관, 축 지정, 덧붙이는 질문, 마무리 문장) |
| `src/memory/memory-rules.ts`, `memory.service.ts` | 규칙은 그대로, 저장은 파일로 |
| `src/review/stats.ts`, `review.view.ts`, `review.service.ts` | 계산은 그대로(답 시작 시간 제외), 화면 대신 문서 |
| `src/interview/calls/*.call.ts` 아홉 개 | 시스템 프롬프트, user 메시지를 만드는 코드, 출력 스키마를 그대로 |
| `src/interview/turn.service.ts`, `src/session/interview.service.ts` | 순서와 거름을 그대로, DB 대신 파일, API 클라이언트 대신 `claude -p` |

- 프롬프트는 여덟 번의 R1 실행과 체크포인트 A·B에서 실제 모델로 다듬은 것이다. 글자를 바꾸지 않는다. 바꿔야 할 곳이 나오면 사용자에게 올린다.

- 지켜야 하는 사용자 판정: `docs/r1-review.md`의 D1~D9, `docs/a-review.md` 1장(질문은 한 번에 최대 둘, 웬만하면 하나), `docs/b-review.md`의 넷째 분류·잘 답함 은퇴·스스로 꺼낸 모름.
- 옮기지 않는 것: 프롬프트 캐싱 설정(CLI가 알아서 캐시한다. 12장), 폴백 모델, SDK의 자동 재시도, HTTP·DB·화면, 답 시작 시간, 진행 중인 면접 여럿(6.1).

## 10. 검증

- **규칙의 단위 테스트**: 앱의 테스트(다음 질문자 고르기, 이름 검사, 세션 규칙, 기억 규칙, 추이, 턴 진행)를 `node:test`로 옮긴다. `aeae0dd`의 테스트에서 옮긴다(스스로 꺼낸 모름의 테스트가 거기 있다).
- **프롬프트 동일성**: 앱의 아홉 호출 함수에 기록용 가짜 LLM을 물려 `{system, user, schema}`를 뽑아 고정 자료로 둔다(`aeae0dd`의 `src`에서). 스킬의 빌더가 같은 입력에서 같은 글자를 내는지 테스트한다. K4를 막는다. **[제안]**
- **한 판의 흐름**: `claudeCommand`를 가짜 실행기로 바꿔 시작부터 복기까지 돌린다. 한도를 쓰지 않는다. 앱의 e2e가 보던 경로(다시 만들기, 되묻기, 덧붙이는 질문, 모름 경로, 뒤 작업이 늦을 때와 죽었을 때, 실패 뒤 이어 하기)를 옮긴다. 더할 경로: 같은 턴의 정답지를 두 프로세스가 쓰려 할 때, `answer`를 두 번 돌렸을 때, 답 파일이 없거나 빌 때, 진행 중인 면접이 있는데 새로 시작할 때.
- **숨김 누출 검사**: 가짜 응답의 숨길 필드마다 표식 문자열을 심고, 면접이 끝나기 전의 모든 명령(시작, 답, 이어서, 상태, 끝나지 않은 면접에 친 복기·고침·표시, 추이)의 표준 출력과 표준 오류에 그 표식이 하나도 없는지 본다. 가짜 실행기가 깨진 JSON을 내거나 비정상으로 끝나는 경우도 넣는다. K1을 막는다. **[제안]**
- **명령줄 길이**: 가장 큰 스키마로 만든 명령줄이 Windows의 한계 아래인지 테스트로 지킨다.
- **실제 한 판**: 먼저 Claude가 지원자 역할로 한 판을 돌려 흐름, 숨김, 답 뒤 대기, 호출 수와 토큰, 권한 창이 뜬 횟수를 잰다. 그 뒤 사용자가 직접 한 판을 한다. **[결정]** 실행 전에 알린다(구독 한도를 쓴다). 사용자가 `/usage`를 앞뒤로 보면 한도를 얼마나 썼는지 알 수 있다.

## 11. 남은 위험과 확인하지 못한 것

- **대기 시간.** 앱은 답 뒤 약 25초였다(측정). 스킬은 호출마다 프로세스를 띄우는 시간(1.6~2.4초, 측정)과 진행자의 턴이 더 붙는다. 진행자의 턴이 얼마나 드는지는 모른다. 첫 실제 한 판에서 잰다.
- **한도 사용량.** 재 본 적이 없다. 첫 실제 한 판에서 잰다.
- **진행자가 답을 옮기다 바꿀 수 있다.** 모델이 글을 옮기는 것이라 글자가 달라질 수 있다. 복기 문서에 저장된 답이 그대로 나오므로 사용자가 볼 수 있다. 문제가 되면 답을 넘기는 방식을 바꾼다.
- **진행자가 평을 하거나 말을 보탤 수 있고(K2), 숨긴 파일을 읽을 수 있다(K1).** 둘 다 지시로만 막는다. 실제 한 판에서 본다.
- **sonnet으로 도는 흘림 검사와 직무 고르기의 품질.** 확인한 적이 없다. 실제 한 판에서 흘림 검사가 기술의 역할을 제대로 가르는지 본다.
- **실패의 종류.** 한도에 닿았을 때, 모델이 거절했을 때, 출력이 스키마와 안 맞을 때 `claude -p`의 결과가 어떤 모양인지 본 적이 없다. 성공한 호출만 봤다. 구분하지 못하는 실패는 `other`가 된다.
- **API 키 인증이 설정 파일로 걸려 있는 경우.** 환경 변수를 지워도 남는다. 점검 명령의 로그인 확인으로만 막는다.
- **CLI 옵션의 변화.** `--safe-mode`, `--json-schema`, `--tools ""`가 바뀌면 깨진다. 점검 명령이 버전, 로그인, 시험 호출을 본다.
- **터미널 CLI에서의 동작.** 확인은 모두 데스크톱 앱에서 했다. 뒤에서 도는 프로세스가 터미널 세션에서도 살아남는지 모른다.
- **권한 창.** 답마다 두 번 물을 수 있다. 실제 흐름에서 세어 본 적이 없다.
- **대화 압축.** `next` 한 줄로 대비했지만 압축된 뒤의 면접을 돌려 본 적은 없다.
- **`${CLAUDE_SKILL_DIR}`.** 문서로만 확인했다. 이 PC에 설치된 스킬 가운데 쓰는 것이 없다. 안 되면 하니스가 넣어 주는 "Base directory for this skill" 줄의 경로를 쓴다.
- **약관.** 구독 로그인으로 `claude -p`를 스크립트에서 되풀이해 부르는 것에 제약이 있는지 확인하지 않았다.
- **두 세션이 같은 면접을 동시에 진행하는 경우.** 막지 않는다. 한 사람이 한 세션에서 쓰는 것을 전제한다.
